Abstract. VisuAlgo+ is a collaborative project to rebuild VisuAlgo with a renewed technical
foundation and a redesigned interface while preserving its educational purpose. My work
focuses on the visualization and interaction layer: graph, tree and sorting visualizers, their
editing and playback behaviour, and their integration into a common interface. The work began
with standalone prototypes and progressed to a single application using a shared panel layout.
This report explains the separation of input, layout and playback state; the V10 panel-group
model; algorithm extensions and their validation; and short explanations placed on the drawing.
The audited application contains 11 graph algorithm identifiers, seven tree workspaces and
eight sorting algorithms. Its recorded validation on 1 November 2026 reports 3,273 passing
unit tests and 151 passing browser cases. These results support functional progress. A Week
10 user trial provided formative feedback and recorded interactions that informed subsequent
UI/UX refinements, including floating text on the canvas. Neither source establishes improved
learning outcomes or comparative usability. The next phase will strengthen interaction testing,
evaluate representative learning tasks and investigate a limited integration with the separate
WebAssembly engine.

1 Introduction and Objectives

1.1 Project background
VisuAlgo provides interactive visualizations of data structures and algorithms. Its original design
brings different topics into a consistent environment and allows students to explore their own
inputs [2]. These strengths are the starting point for VisuAlgo+.
In an early discussion, A/P Steven Halim described the existing Laravel/PHP, MySQL, D3 and
jQuery stack and encouraged us to explore a modern foundation for both the interface and execution
engine. This background reflects my account of that discussion [8]. The rebuild retains useful
technologies, including D3 for selected layout and animation tasks.
The aim is a modern successor that preserves VisuAlgo’s educational purpose and useful interactions
while supporting future development. The current deliverable is an experimental application, not
yet a full replacement.

1.2 Personal motivation and role
My motivation for joining VisuAlgo+ comes from my background in competitive programming and
teaching. Participating in many programming competitions and achieving strong results has given
me substantial experience with algorithms and data structures. Teaching students passionate about
competitive programming has helped me explain these concepts from different perspectives and
recognize where learners need clarification.
I hope to apply both experiences to VisuAlgo+’s user interface and user experience, helping learners
follow why an algorithm makes a decision, how its state changes, and how those changes produce
the result. This perspective guides which intermediate states I show, how I connect drawings with
pseudocode, and where short explanations could clarify a step.
My initial responsibility is the visualization and interaction layer for graph algorithms, tree-based
data structures and sorting algorithms. This includes developing the visualizers, supporting input
editing and step-by-step playback, and integrating them into a consistent interface. Working with
Kerk on the shared design and integration, I aim to turn my algorithmic knowledge and teaching
experience into practical improvements that can later be evaluated with learners.

1.3 Objectives and current scope
The project has five working objectives:
1. Select suitable modern and widely adopted technologies for rebuilding the platform.
2. Preserve useful algorithm exploration, input editing and step-by-step explanation from VisuAlgo.
3. Provide a consistent interface across different algorithm and data-structure modules.
4. Establish clear boundaries for extending visualizers and integrating execution engines.
5. Validate the rebuilt functionality and identify what still requires technical and user evaluation.
Kerk Tai Heng, a fellow FYP student under the same supervisor, works on the engine/WASM
foundation, website design system and shared infrastructure. Section 3 details our contributions and
collaboration.
The current application targets desktop and laptop use. It runs TypeScript algorithm implementations
in the browser. The separate WebAssembly engine has not been connected to these visualizers.
Mobile design, complete feature parity with VisuAlgo and measured learning improvement are
outside the completed work reported here.

2 Background and Related Work

2.1 Algorithm visualization and educational use

Halim et al. [2] present VisuAlgo as a unified web-based environment for learning algorithms. Support
for user-defined inputs and consistent interaction across topics is particularly relevant to this project.
A reconstruction should preserve these properties even when the rendering technology and page
layout change. Reusing familiar examples and algorithm operations also provides a useful reference
when checking the rebuilt functionality.
However, a working animation is not sufficient evidence of learning benefit. Hundhausen, Douglas
and Stasko’s meta-study of 24 studies [3] found that how learners used algorithm visualizations
mattered more than their graphical characteristics alone. This motivates a distinction between two
questions in VisuAlgo+: whether the software behaves correctly, and whether students can use it
to understand and explain an algorithm. The present tests primarily address the first question.
The Week 10 trial provided initial formative input; a more structured follow-up is proposed for the
second.
OpenDSA combines visualizations with explanatory material, interactive exercises and proficiency
assessment [4]. It illustrates how visualization can form one part of a wider learning activity.
VisuAlgo+ currently concentrates on exploration: editing inputs, stepping through execution,
following pseudocode and inspecting state. It does not yet provide an equivalent assessed learning
sequence. Therefore, the current contribution should be judged as a visualization foundation rather
than a complete instructional system.

2.2 Reusable platforms and implementation choices

Shaffer et al. [5] survey the algorithm-visualization field and discuss issues including availability,
quality and topic coverage. Their historical survey helps motivate attention to maintainable
implementations and reusable interaction patterns. It does not establish the current quality of
VisuAlgo+ or prove that a shared shell is educationally superior. Those claims require evaluation of
this implementation.
For the technical foundation, React Flow supplies an interactive node-and-edge canvas [9]. The
project builds algorithm-specific state, edge identities and presentation rules above that canvas.
D3 supplies narrower computational tools: force simulation for graph positions and a hierarchy
layout for trees [1]. This combination separates the computation of positions from the ownership of
application state. Sorting uses Canvas 2D because its main representation is an array of bars rather
than an editable graph.

2.3 Position of this work

The project applies established algorithm, rendering and interface ideas to a practical rebuild. Its
current value lies in connecting them coherently: a stable editable document, reproducible playback,
shared page controls, and explanations tied to individual algorithm steps. Dockable panels and
low-link algorithms are not claimed as new research techniques.
Three design questions guide the work. First, how can editing and playback share one canvas
without accidentally invalidating or corrupting an execution? Second, how can different topics share
a layout while preserving their own interactions? Third, how can a step remain understandable
when it changes internal state but produces little visible motion? Sections 4.2–4.8 describe the
implemented responses. The Week 10 trial provided initial usability feedback; systematic follow-up

3 Development Approach and Responsibilities

3.1 From standalone prototypes to one application

The first stage explored interaction behaviour in standalone repositories. Graph Visualizer V1 began
on 28 July; Graph Visualizer V2 followed in August with a clearer separation of document, layout
and playback state. Sorting and tree prototypes explored different representations and operation
models. This work provided a functional base before integration with the shared website.
During September and October, I adapted these visualizers to Kerk’s design system. Kerk conducted

our supervisor and I agreed on V10 as a combined design adapted from V2 and V7, retaining selected

The survey therefore served as formative input to the design process, while V10 emerged from our

4 System Design and Implementation

4.1 Architecture of the current application

The current build is one React and TypeScript single-page application assembled with Vite. The
site layer owns routing, the top bar and the theme. A module page hosts the graph, tree or sorting
visualizer. Each visualizer owns its data, algorithm execution and playback state, while shared
components provide common layout and presentation utilities [6].

                                 Site host: routing, top bar and theme

            Document and run             Operations and run              Generators and clock

                                  graph/tree step-note presentation



                     Rendering: React Flow for graph/tree; Canvas 2D for sorting

Figure 1: Current application boundaries. The lower dashed box is a separate prototype, not a dependency
of the visualization application.


This organization avoids making the shared shell responsible for algorithm logic. For example, the
shell positions a Status panel, but the active algorithm determines its content. Similarly, the site
can change a theme without taking ownership of a graph run. State is held in the browser; saved
layout preferences use local storage.
The graph and tree canvases use React Flow, with D3 handling force-directed and hierarchical
positions respectively. Sorting uses Canvas 2D with interpolation utilities. These choices reflect
different interaction needs rather than an attempt to force every module into one renderer. The
technology change is consequently selective: reusable modern application components coexist with
useful existing visualization libraries.
The architecture provides a place for later engine integration, but it does not already implement

4.2 State ownership and reproducible playback

The graph foundation separates four concerns (Table 2). A persistent canvas is reused for editing
and execution. Starting a run derives a sequence of typed steps from the current document; stepping
through that sequence derives the visible presentation. This reduces the risk of keeping a separate
editing graph and animation graph that gradually disagree [6].

                           Table 2: State separation in the graph visualizer.

State owner          Responsibility                                Example consequence

Graph document       Vertices, edges, weights, stable identities   A semantic edit invalidates the previous
                     and topology revision.                        run.
Graph layout         Positions and pinned vertices.                Dragging a vertex changes the drawing
                                                                   without changing the algorithm input.
Run session          Step sequence, current index, run identity    An outdated timer event cannot advance
                     and playback status.                          a newer run.
Presentation         Highlights, badges and derived edge/node      Rewinding restores the presentation of the
                     styles.                                       selected step.


For example, moving vertex B should not change a shortest-path computation. Changing an edge
weight should. Keeping position data separate from semantic input makes this distinction explicit.
A run identity also protects against asynchronous playback events that arrive after the user stops or
replaces a run.
Graph and tree algorithms build their complete step sequence when a run starts. The session then
moves between idle, paused, playing and finished states. Each selected step supplies consistent
information for the drawing, pseudocode highlight and status text. This eager approach makes
backward stepping and seeking straightforward, but increases startup time and memory use for long
runs. These costs have not yet been benchmarked.
Tree operations add a distinction between a preview and a committed document. An insertion or
deletion can be explored through intermediate states before its final result is applied. This lets the
learner inspect an operation without treating every animation frame as a permanent edit. Clear
Apply behaviour is therefore part of the interaction model, not just a rendering detail.

4.3 Sorting uses a different execution model

Sorting produces operations from generators. A shared clock advances one, two or four panes, each
with its own operation stream. The implementation retains executed history, buffers up to 2,048
future operations, and initially primes streams up to a 60,000-operation aggregate threshold before
continuing lazily. Seeking backwards reconstructs the state from retained operations; it does not
rely on stored checkpoints.
This approach avoids requiring every sort to finish generating before interaction begins. However,
retained history remains unbounded, and distant seeks can require substantial replay. These are
explicit limitations for future measurement. A common operation index supports synchronized
inspection, but operations from different algorithms are not equivalent units of computational cost.
The comparison view must therefore not be interpreted as a wall-clock performance benchmark.

4.4 V10: a shared panel-group layout

The V10 shell organizes supporting information around a fixed central canvas. The canvas cannot
become a tab. Left, right and bottom regions contain groups of tabs; a user can move a panel into
a group, split it into another group or place it in an empty region. The default arrangement puts
Action and e-Lecture on the left, with Pseudocode and Status on the right [6].

The main engineering decision was to express layout changes in a pure model rather than embedding
all rules inside pointer-event handlers. The model preserves panel membership, removes empty
groups and ensures that each group’s active tab belongs to that group. Required panels occur exactly
once, optional panels at most once, and groups do not nest.
A common layout resolver is used for sizing, target validity and drag previews. A proposed move is
first represented in the model and then resolved into geometry, so the preview and committed result
use the same constraints. Groups have minimum dimensions of 240 pixels in width and 120 pixels in
height; the drawing has a target floor of 360 by 320 pixels when the viewport can accommodate it.
This is not an unconditional guarantee on very small windows.
Saved layouts are versioned and repaired or replaced with defaults when invalid. Model tests include
4,000 seeded random operations, checks across multiple viewport sizes, and repeated serialization
round trips. This validates many structural transitions, but does not replace browser testing of
pointer coordinates, drag feedback and actual resizing. The current automated coverage of those
interactions is incomplete.

Figures 3 and 4 show why layout is part of algorithm interaction. A learner may need more space

three visualizer families.

could disagree with the final arrangement, or saved state could no longer fit a window. The explicit
invariants and shared resolver address these risks at the model level. Systematic browser coverage of
tab joining, splitting, cancelling and restoring layouts is a priority for the next phase.

4.6 Graph extensions and algorithm validation

The current graph module contains 11 algorithm identifiers. Alongside BFS, stack-based DFS,
Dijkstra, Kruskal and Edmonds–Karp, the application supports recursive DFS, Bellman–Ford, Prim,
topological sorting, bipartite checking, and cut-vertex/bridge detection. Topological sorting offers
DFS and Kahn methods; bipartite checking offers DFS and BFS methods. The traversal interface
also supports an End node where applicable [8].
These additions extend both computation and explanation. Recursive DFS exposes a different
execution structure from a stack-based traversal. Topological sorting and bipartite checking provide
witnesses when the input violates their conditions, rather than displaying only a final success or
failure. Bellman–Ford and Prim were planned and built with Codex under my requirements and
review.




Figure 5: Final frame of cut-vertex and bridge detection on the CP4 4.7 example. The reported cut vertices
are 1, 3 and 4; the bridges are 0–1 and 3–4.


A representative correctness issue: parallel edges. A low-link DFS must skip the parent
edge, not every edge leading to the parent vertex. If two vertices are joined by two parallel edges,
removing either edge leaves them connected. Ignoring both edges during DFS can incorrectly mark
one as a bridge. Stable edge identities make the intended rule explicit.
For validation, the tests compare results with independently formulated oracles. Cut vertices and
bridges are checked by removing a vertex or edge and recomputing connected components. Bellman–
Ford is checked against Floyd–Warshall-based results, including negative-cycle reachability. Prim
is compared with exhaustive forest candidates on small inputs. These oracles are algorithmically
different from the implementations under test; this reduces shared assumptions, but is not a formal
proof.
The recorded randomized cases include 700 graph inputs for cut-vertex/bridge checks, 140 signed
graphs for Bellman–Ford, and 20 small graphs for Prim tested from every start vertex. Topological
and bipartite methods have additional randomized checks [7]. Fixed seeds make failures reproducible.
Small exhaustive cases complement, rather than replace, larger representative examples.

4.7 Tree operations and sorting comparison

The tree visualizer provides seven workspaces: LCA, BST, AVL, Heap, Trie, Segment Tree and Lazy
Segment Tree. Work includes BST/AVL queries and traversals, AVL deletion, heap operations, and
lazy range-add/range-sum behaviour. The heap links array and tree representations; intermediate
changes remain previews until applied. These workspaces do not imply complete operation parity
with VisuAlgo [8].

Sorting provides eight algorithms in a one-pane Study mode and two- or four-pane Compare mode.

4.8 Floating text: explanations on the canvas

A step can be meaningful even when the drawing hardly changes. For example, Dijkstra may reject
a relaxation because the existing distance is already smaller. If the reason appears only in a separate
Status panel, the learner must repeatedly look away from the relevant edge. Following the Week 10
trial, I introduced floating text: short explanations beside the relevant node or edge [8, 6]. This was
an important post-trial UI/UX update, intended to minimize how often users need to look at Status
while following visualization steps and keep their attention on the canvas. It follows Prof. Halim’s
canvas-focused educational goal, as recalled in our project discussions. Status remains available for
persistent detail; reduced attention switching is a design aim, not a measured result.




Figure 8: Dijkstra relaxation from B to E: the note explains that 4 + 3 < 8, so E’s distance changes from 8
to 7. The nearby explanation complements the persistent Status panel.


The implementation has a shared note description, placement calculation, timing logic and rendering
layer. Graph and tree algorithms supply the semantic content; the shared layer controls how it is
displayed. Current coverage includes Dijkstra, LCA, BST, AVL and Heap. Sorting, Trie, segment
trees and the other graph algorithms do not yet use this layer.
Notes are rendered outside the graph transform so their text remains at a constant screen size while
the anchor follows the relevant node or edge. Placement checks nearby obstacles, including node
badges and edge-weight labels. It first tries preferred positions, then alternatives; when none is clear,
it uses a minimum-overlap fallback. Dense graphs can therefore still produce overlap.
Timing adapts to playback. A manually inspected note normally lasts 1,600 milliseconds. During
autoplay, its duration is limited by the step interval and configured delay; notes are suppressed for
intervals below 200 milliseconds. This avoids accumulating unreadable text at high speed. Persistent
Status text remains available, so the short-lived note is supplementary.
The design is an implemented response to an explanation problem, not evidence that attention or
learning has improved. The note layer is currently hidden from accessibility APIs, and the application
has not undergone a systematic accessibility evaluation. Future work should check whether the

6 User Evaluation, Limitations and Next Steps

6.1 Week 10 formative user trial

In Week 10, Kerk and I invited several users to use VisuAlgo+ V10 independently for 15–20 minutes.
We recorded their interactions on video, administered a short test afterwards and collected feedback.
Participants varied in prior use of VisuAlgo.net, from frequent to infrequent users, and in algorithm
experience, from experienced competitive programmers to beginners.
The sessions yielded positive feedback as well as areas needing improvement. Reviewing the
recordings helped us identify interactions that supported familiarization with the new interface and
places needing refinement. This informed subsequent UI/UX work, including floating text to keep
explanations close to the visualization (Section 4.8). The trial was separate from Kerk’s earlier
V2/V7 survey and the subsequent joint decision to adopt V10.

6.2 Evidence boundaries and implementation limits

This account follows my clarification on 4 November 2026. A shared-folder screenshot shows
prototype-testing video files, but participant numbers, test questions, scores, detailed feedback and
coded observations are not included here. The trial provides formative design input; a post-use test
alone does not establish learning gains or comparative usability. The effect of floating text has not
been measured. Performance benchmarks and a test-coverage percentage are also unavailable.
Several implementation limits are material. Graph and tree runs build eager timelines. Sorting
retains unbounded history and replays operations when seeking. Step notes cover only selected
algorithms and may overlap in dense drawings. Browser validation is concentrated on desktop
Chromium; mobile behaviour, cross-browser compatibility and accessibility remain incomplete.
Separate developer checks also lack a complete recorded protocol; they should not be conflated with
the Week 10 user trial.
The separate engine is also a scope boundary. My unmerged engine experiment explored stable edge
identity and a reusable browser client for worker/RPC lifecycle management. It helped identify
integration requirements, but is not part of the deployed visualizer path. Presenting the current
application as WASM-powered would therefore be inaccurate.

6.3 Proposed follow-up evaluation

First organize the Week 10 footage, test responses and feedback into anonymized observations
linked to design changes. Then conduct a more structured follow-up, provisionally involving 6–10
students familiar with introductory data structures. The participant plan and arrangements should
be discussed with the supervisor before recruitment. A small study can identify interaction problems;
it cannot establish general learning effectiveness.

Use a fixed machine and production build with saved inputs of increasing size. Measure run
preparation, time to first visible step, seek latency, playback frame pacing and memory use. Repeat
each condition at least five times and report the median together with the spread and environment.
These measurements should guide whether checkpointing, bounded history or a different execution
boundary is necessary.

7.1 Integration strategy and risks

Engine integration should begin with one vertical slice: graph input, engine execution, typed step
conversion, rendering and backward/forward playback. The first milestone is behavioural agreement,
including edge identities and cancellation, rather than replacing every TypeScript algorithm. If the
engine contract or schedule is not ready, the existing implementation remains a functional baseline
and the report can document the integration study separately.
The main technical risks are the cost of long timelines, inconsistent semantics between modules,
and interaction failures that model tests do not expose. Measurements should precede a major
playback redesign. Shared abstractions should be introduced only where behaviour is truly common;
graph/tree eager sequences and sorting generators already demonstrate that identical controls need
not imply identical execution internals.
The main project risk is scope growth. Adding every unfinished catalogue topic would reduce time
for evaluation and refinement. I propose prioritizing the current graph, tree and sorting workflows,
selected explanation gaps and a small engine experiment. Further features should be chosen with
the supervisor according to educational value, missing coverage and available time.

7.2 Expected outcome

By the final assessment, the intended outcome is a documented and tested visualization foundation
with a coherent interface, representative algorithm coverage, evidence from user tasks and technical
measurements, and a clear account of engine integration progress. The first-semester work establishes
the implementation base. The next phase should explain where it works well, where it fails, and
which improvements are supported by evidence.
